# CLAUDE.md — OptimaX (Rust): діагностика й оптимізація ігрових ПК

Цей файл є обов'язковим набором правил. Порушення правил = некоректна робота. Якщо правило суперечить запиту користувача — спочатку зупинись і запитай.

---

## 1. Суть проєкту

Windows 10/11 утиліта, яка **вимірює**, що обмежує продуктивність у іграх, і **доводить цифрами** ефект кожної зміни. Орієнтована на хороші ПК, де класичні твіки реєстру майже нічого не дають.

Головний принцип: **жодного плацебо**. Немає виміряного ефекту — немає рекомендації. Якщо покращувати нічого, програма чесно це каже.

Мова інтерфейсу: українська (i18n-ready, рядки не хардкодяться в логіку).

## 2. Стек (не змінювати без дозволу)

- **Мова:** Rust stable, edition 2021+. Портативна збірка: головний exe + вбудований PresentMon (див. 2.1). Рантайм-залежність одна: WebView2.
- **Workspace:** Cargo workspace з окремими крейтами.
- **Системне:** крейт `windows` (реєстр, WMI, служби, плани живлення), `sysinfo` (CPU по ядрах, RAM, процеси), NVML (NVIDIA).
- **Frametime:** запуск PresentMon CLI (бандл, див. 2.1) + парсинг CSV. Власний ETW (`ferrisetw`) лише за окремим завданням.
- **UI:** Tauri 2 (Rust-бекенд + веб-фронтенд). Фронтенд: TypeScript (strict), Vite, без важких UI-фреймворків. Дозволено Svelte або чистий TS + Web Components.
- **Серіалізація:** `serde`, `serde_json`. Помилки: `thiserror` (бібліотеки), `anyhow` (лише в `main`/UI-шарі). Логи: `tracing`.
- **Маніфест:** `requireAdministrator`.

### 2.1 Зовнішні бінарники та рантайм

- **PresentMon — бандлимо**, користувач нічого не кладе сам. Версія зафіксована, SHA-256 лежить у `crates/frametime/presentmon.sha256` (і в коді як константа).
- Хеш перевіряється **двічі**: при збірці (build-скрипт) і **перед кожним запуском** у рантаймі. Не збігся — не запускати, показати помилку, залогувати.
- Заборонено: докачування PresentMon з мережі, запуск бінарника з іншого шляху, підміна версії без оновлення хеша й запису в CHANGELOG.
- Перед бандлом перевірити ліцензію PresentMon і додати її текст у `THIRD_PARTY_LICENSES`.
- PresentMon розпаковується в каталог даних програми (`%LOCALAPPDATA%\OptimaX\bin`) із правами запису лише для адміністратора.
- **WebView2:** на Win11 є вбудований, на Win10 майже завжди є. Рантайм його **наявність перевіряє** при старті. Якщо немає — зрозуміле повідомлення з кнопкою встановлення (офіційний Evergreen-бутстрапер, лише за згодою користувача), а не падіння.
- Документація та README не повинні казати «один exe без залежностей»: правильне формулювання — «портативна збірка, потрібен WebView2».

Нові залежності додавати лише з обґрунтуванням (навіщо, розмір, ліцензія, підтримка). Ліцензії: MIT/Apache-2.0/BSD. GPL — заборонено.

## 3. Структура workspace

Корінь репозиторію (`PcOptimize`) **є** коренем workspace. Вкладеної папки `optimax/` не створювати.

```
./                           # корінь репо = корінь workspace
├─ CLAUDE.md
├─ .gitignore                # target/, .idea/, ui/node_modules/, ui/dist/
├─ Cargo.toml                # workspace
├─ crates/
│  ├─ core/                  # спільні типи, помилки, конфіг
│  ├─ metrics/               # збір CPU/GPU/RAM/диск/температури
│  ├─ audit/                 # аудит конфігурації
│  ├─ frametime/             # PresentMon, FPS, 1% low, піки
│  ├─ diagnosis/             # правила вузького місця + впевненість
│  ├─ tweaks/                # застосування змін + відкат
│  ├─ gamemode/              # режим гри, профілі ігор
│  ├─ network/               # мережа: адаптер, Wi-Fi, затримка й втрати (замір лише за кнопкою)
│  ├─ upscale/               # апскейл (ОСТАННІЙ етап)
│  └─ app/                   # Tauri backend (команди, події)
└─ ui/                       # фронтенд
```

Правила залежностей: `app` залежить від усіх; доменні крейти **не** залежать від `app` і **не** залежать від UI. `diagnosis` не торкається системних викликів — приймає лише дані (чисті функції, легко тестувати).

## 4. Порядок роботи (суворо)

1. Скелет workspace + `core` + `metrics` + `audit`
2. `frametime` + `diagnosis`
3. `tweaks` (відкат) + A/B-тести
4. `gamemode`
5. Tauri-інтерфейс (`app` + `ui`)
6. `upscale` — **тільки в кінці**. Генерація кадрів — лише як експеримент після всього.

Не починай наступний етап, поки поточний не компілюється, не проходить тести й не відповідає розділу «Definition of Done». Не роби великих змін «заодно» — один етап за раз.

## 5. Безпека та відкат (найвищий пріоритет)

1. **Кожна зміна системи оборотна.** Перед застосуванням зберегти стару стан-значення в JSON-журнал (ключ, ім'я, тип, старе значення, час). Відкат одним викликом.
2. Перед першим застосуванням у сесії — створити **точку відновлення Windows**.
3. **Показувати до застосування:** що змінюється, де (ключ реєстру/служба/план), старе та нове значення, вплив на продуктивність, нагрів і безпеку.
4. Заборонено за замовчуванням: вимикати Windows Defender, VBS/HVCI, UAC, брандмауер, оновлення, телеметрію через небезпечні методи. Лише як явна «експертна» опція з червоним попередженням і підтвердженням.
5. Жодних змін без явного підтвердження користувача. Жодних дій «у фоні» без видимого запису в журналі.
6. **Жодної телеметрії**, мережевих викликів без потреби, автозапуску без згоди.
7. Заборонено: завантаження з мережі й запуск сторонніх бінарників; запуск бандл-бінарників (PresentMon) без перевірки SHA-256 безпосередньо перед стартом; редагування загальних системних файлів; зміни BIOS/UEFI; андервольт/розгін автоматично.
8. При збої посеред зміни — автоматичний відкат і запис помилки в журнал.
9. Реєстр: читати → перевіряти тип → писати. Ніколи не писати «наосліп».

## 6. Чесність результатів

- Жодних обіцянок приросту без вимірювання.
- Діагноз завжди з **рівнем впевненості** (0–100%) і списком доказів. Не вигадуй причину, якщо даних недостатньо — так і скажи.
- A/B-тест: мінімум 3 прогони «до» і 3 «після», показувати середнє, 1% low, розкид. Приріст менший за похибку вимірювання = «ефекту немає», зміна відкочується.
- Умови тесту мають бути однаковими (та сама сцена/час, прогрів, температура). Якщо вони відрізняються — попередити.
- Не використовувати маркетингові формулювання («прискорить у 2 рази») у UI.

## 7. Правила Rust-коду

- `#![forbid(unsafe_code)]` у всіх крейтах, крім тих, де `unsafe` неминучий (FFI до `windows`/NVML). Там — мінімальні `unsafe`-блоки з коментарем `// SAFETY:` і безпечною обгорткою.
- Заборонено `unwrap()`/`expect()`/`panic!` у продакшн-коді (дозволено в тестах). Усі помилки — через `Result`.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` мають проходити без зауважень.
- Публічні типи й функції — з doc-коментарями.
- Системні виклики ховати за трейтами (`RegistryApi`, `PowerApi`, `GpuApi`…), щоб логіку можна було тестувати моками на будь-якій ОС.
- Блокуючі операції — не в UI-потоці. Збір метрик в окремих потоках/задачах, канали для передачі даних.
- Збір метрик має бути **легким**: програма не повинна помітно навантажувати систему під час гри (ціль: <1% CPU, без GPU-навантаження в режимі моніторингу).
- Жодних глобальних змінних зі змінним станом без обґрунтування.

## 8. Перевірка та середовище

Розробка може вестись не на Windows. Тому:
- Обов'язково: `cargo check --workspace --target x86_64-pc-windows-gnu` (або msvc, якщо доступно) і `cargo test` для платформонезалежної логіки (`diagnosis`, парсинг CSV, відкат, статистика).
- Ніколи не стверджуй, що код «працює на ПК», якщо його було лише скомпільовано. Чітко розділяй: «компілюється» / «покрито тестами» / «перевірено на реальному Windows».
- Те, що потребує реального заліза (NVML, PresentMon, реєстр), позначай у звіті як **потребує перевірки користувачем** і давай короткий чекліст перевірки.

## 9. Діагностика: правила вердиктів

Мінімальний набір правил (кожне — окрема чиста функція з тестами):

- **GPU-bound:** завантаження GPU ≥ 95%, FPS чутливий до роздільності.
- **CPU-bound:** GPU < 90%, одне ядро ≥ 95% (аналізувати **кожне ядро**, не середнє).
- **VRAM:** використання > 90% і піки frametime збігаються зі зростанням shared-пам'яті.
- **Тротлінг:** падіння частоти разом із температурою/power limit (NVML причини тротлінгу).
- **Мікрофризи:** 1% low значно нижчий за середній FPS; аналіз вікна ±200 мс навколо піків (диск, фоновий процес, DPC).
- **Фоновий процес:** процес з помітним CPU під час гри (напр. chrome.exe 13%).
- **Конфігурація:** RAM нижче XMP/EXPO, Гц монітора нижчий за максимум, PCIe x4/x8, Resizable BAR вимкнено, старий драйвер.

Формат вердикту: `{ category, severity, confidence, evidence[], suggested_fix?, expected_gain: Option<..> }`. `expected_gain` заповнюється лише після реального вимірювання.

## 10. Фронтенд: дизайн-система

### 10.1 Загальний стиль
Сучасний, темний, «преміум-інструмент» у дусі наданих скриншотів: бічна навігація ліворуч, контент справа, картки зі скругленнями, градієнтний акцент, моноширинний журнал дій унизу. Зробити **чистіше й сучасніше**: більше повітря, м'які тіні/світіння, плавні переходи. Без візуального шуму.

Макет вікна:
- Заголовок вікна з іконкою й назвою «OptimaX by X44TO».
- Сайдбар ≈ 225px: логотип, групи «Головне / Пристрій / Інструменти / Система», активний пункт підсвічений.
- Контент: заголовок сторінки + підзаголовок, далі картки.
- Нижня панель дій (sticky): ліворуч вторинні дії, праворуч головна.
- Статус внизу сайдбара: індикатор (жовта/зелена крапка) і версія.

### 10.3 Компоненти
- **Картка:** `--bg-card`, 1px `--border`, радіус `--radius-lg`, ледь помітний внутрішній градієнт; hover — підсвітка межі.
- **Кнопки:** primary — градієнт `--accent-from → --accent-to`, світіння `--accent-glow` при hover; secondary — прозора з межею; danger — `--danger`. Стани: hover, active (scale .98), focus-visible (кільце), disabled, loading.
- **Перемикач (toggle):** плавна анімація кружка, акцентний градієнт у ввімкненому стані.
- **Сегментований контроль** (Майстер / Експерт, 30 с / 60 с / 120 с).
- **Бейджі впливу:** червоний «Впливає на звичні речі», жовтий «Помірний вплив», синій «Безпечно» — завжди з крапкою-індикатором і текстом (не лише колір).
- **Радіо-картки** для майстра (вибір типу ПК), прогрес «Крок N з M» градієнтною смугою.
- **Кільцеві індикатори** (напр. 31% оптимізація, 75% приватність) — SVG-кільце з анімацією заповнення.
- **Журнал дій:** моноширинний, зелені ✓ для успіху, автопрокрутка, не більше 500 рядків у DOM (віртуалізація/обрізання).
- **Блок «Що зміниться»:** розкривний, показує ключ реєстру/службу, старе → нове значення моноширинним шрифтом.
- **Перевірка збірки:** список знахідок із кольоровою крапкою та кнопкою дії.

### 10.4 Фонова анімація: пульсуюче коло з точок (ОБОВ'ЯЗКОВО)

Фірмовий елемент: на фоні головного екрану (Аналіз/Діагностика) — велике **коло, складене з точок**, з **градієнтним забарвленням** (`--accent-from → --accent-to`) і **м'якою пульсацією**.

Вимоги до реалізації:
- Рендер: `<canvas>` (2D) або WebGL, розташований `position: fixed; inset: 0; z-index: 0; pointer-events: none`. Контент — поверх, з `z-index: 1`.
- Геометрія: точки розташовані концентричними кільцями (полярна сітка), кількість точок ≈ 600–1200 залежно від розміру вікна. Радіус кола ≈ 35–45% меншої сторони вікна, центр — зміщений до центру контентної області, не під сайдбар.
- Колір: градієнт за кутом/радіусом від `--accent-from` до `--accent-to`, прозорість точок 0.15–0.7, зовнішні кільця світліші/прозоріші.
- Пульсація: хвиля, що розходиться від центру назовні (синусоїда за відстанню від центру + час), амплітуда зміни радіуса точки 15–30%, період ≈ 4–6 с, `ease` плавний. Легке «дихання» всього кола (масштаб ±2%).
- Додатково (м'яко): повільне обертання кілець у різні боки (≈ 1–3°/с), легкий параллакс від курсору (≤ 8px).
- Загальна яскравість приглушена: анімація **не повинна заважати читанню** тексту. Поверх canvas — легка віньєтка/затемнення до `--bg-app` на краях.
- Реакція на стан: у спокої — повільна пульсація; під час діагностики/сканування — швидша хвиля й яскравіший акцент; при знайденій проблемі — коротка тепла (`--warn`) хвиля; при успіху — зелена (`--ok`) хвиля. Перехід між станами плавний (інтерполяція параметрів ≥ 400ms).

**Жорсткі обмеження продуктивності** (це програма для оптимізації — вона не має сама створювати навантаження):
- Ліміт 30 FPS для фону (за потреби 60 лише при взаємодії), `requestAnimationFrame` з throttle.
- **Анімація повністю вимикається**, коли: вікно згорнуте/не у фокусі (`document.hidden`, `visibilitychange`), увімкнено режим гри, йде A/B-бенчмарк або запис frametime, користувач ввімкнув «Економний режим» у налаштуваннях.
- Поважати `prefers-reduced-motion: reduce` — статичний кадр замість анімації.
- Один canvas, один цикл рендера; без аллокацій у кадрі (переиспользувати масиви/`Float32Array`); `devicePixelRatio` обмежити до 2.
- Для кількості точок застосувати автоматичне зниження якості, якщо середній час кадру фонового рендера > 6 мс.
- Бюджет: <2% CPU і мінімальне навантаження GPU у стані анімації. Виміряти й вказати результат у звіті.
- Налаштування в UI: «Анімація фону: Висока / Низька / Вимкнена».

### 10.5 Інші анімації
- Лише `transform` і `opacity` (без анімації `width/height/top/left`).
- Тривалість 120–400 мс, `--ease`. Поява сторінок: fade + зсув на 8px. Заповнення кілець/прогресу — плавне.
- Усі анімації мають вимикатися за `prefers-reduced-motion`.

### 10.6 Доступність і UX
- Повна навігація клавіатурою, видимий `focus-visible`.
- `aria-label` для іконок-кнопок, `role="switch"` для toggle, `aria-live="polite"` для журналу/статусів.
- Мінімальний розмір вікна 960×640; адаптація під масштаб Windows 100–200%.
- Деструктивні/системні дії — модальне підтвердження з описом наслідків.
- Стани «завантаження / порожньо / помилка» продумані для кожного екрана.
- Жодних зовнішніх ресурсів (CDN, шрифти, аналітика). Працює офлайн.

### 10.7 Екрани (мінімум)
Аналіз · Оптимізація (Майстер + Експерт) · Ігри (режим гри, мої ігри) · Діагностика («Чому лагає?», результат, журнал) · Залізо · Ноутбук · Мережа · Очищення · Програми · Автозавантаження · Вигляд · Резервні копії · Налаштування.
Екран «Апскейл» додається лише на етапі 6.

### 10.8 Зв'язок UI ↔ бекенд
- Лише через Tauri-команди та події; у фронтенді жодної бізнес-логіки діагностики.
- Типи команд/подій генерувати зі спільних Rust-типів (наприклад, `specta`/`ts-rs`), щоб уникнути розбіжностей.
- Довгі операції — з прогресом і можливістю скасування.

## 11. Апскейл (останній етап — не чіпати раніше)

- Захоплення вікна: Windows Graphics Capture; вивід: wgpu/DirectX в окремому оверлеї.
- Шейдери: integer scaling, Lanczos, FSR 1 (MIT), NIS, різкість.
- Інтеграція з діагностикою: GPU-bound → рекомендація «знизити внутрішню роздільність + апскейл»; CPU-bound → чесно сказати, що апскейл не допоможе.
- Генерація кадрів — лише експеримент, окремий feature flag, з чесним попередженням про затримку й артефакти.
