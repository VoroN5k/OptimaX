# «Що робити далі»: від результату діагностики до перевіреної зміни

Дата: 2026-11-16. Статус: чернетка на погодження.

## Навіщо

Людина записала гру й бачить результат: вердикт, кільце, графіки, поради текстом. Далі вона
не знає, що робити: порада закінчується словами («знизьте важкі налаштування»), кнопка є лише в
знахідки про апскейл, а наявні інструменти перевірки («Порівняння» з ABBA, порівняння записів в
«Історії») з результату не видно. Мета — замкнути ланцюжок **порада → зміна → цифра, чи
допомогло**, і прибрати з результату те, що заважає його прочитати.

Охоплює три пункти, які обрав користувач:
1. Наступний крок під порадою + автоматичне порівняння з попереднім записом (варіант «А + Б»).
2. Результат без дублювання; експертні розбори — в одній згортці.
3. Чесні бейджі й кільце на «Головній».

## Цілі / не-цілі / анти-цілі

- **Цілі:** кожна порада, яку людина може перевірити зміною в грі, має кнопку A/B; після
  повторного запису тієї самої гри результат сам каже, що змінилося, з порогом шуму; порада
  показується один раз; бейдж інформаційної знахідки не виглядає як «усе добре / безпечно».
- **Не-цілі:** нові правила діагностики; зміна порогів вердиктів; «майстер» на кілька екранів;
  автоматичне застосування налаштувань гри; англійська мова.
- **Анти-цілі (провал, навіть якщо працює):** обіцянка приросту до вимірювання; видавати
  порівняння «один запис проти одного» за доведений ефект (CLAUDE.md розд. 6 — доказ лише A/B);
  бізнес-логіка вибору кроку чи попереднього запису у фронтенді (CLAUDE.md 10.8).

## Обмеження

- Вердикти, кроки й вибір попереднього запису визначає бекенд; фронтенд лише малює.
- Знахідки зберігаються в історії (JSON-файли) — нове поле мусить мати `#[serde(default)]`,
  старі записи читаються без змін.
- Типи для UI генеруються ts-rs (`cargo test -p optimax-app`).
- Стиль — `docs/DESIGN.md` і CLAUDE.md розд. 10 (токени, текст + іконка, не лише колір).

## Підходи (розглянуто)

| | Суть | Плюси | Мінуси |
|---|---|---|---|
| А | Кнопка під порадою: «Перевірити A/B» відкриває «Порівняння» з грою й варіантами | найчесніше (ABBA, ≥3 прогони) | людина мусить перемикати налаштування між прогонами |
| Б | «Змінив щось — запиши знову»: новий результат сам порівнюється з попереднім записом гри | природна поведінка, одна дія | один запис проти одного, менш надійно |
| **В = А + Б** | обидва | покриває і звичну поведінку, і доказ | трохи більше роботи |

**Обрано В** (користувач, 2026-11-16): більшість людей просто змінить налаштування й запише знову —
це підхоплює Б; хто хоче доказ — кнопка A/B. Обидва перевикористовують наявний код (пресет
«Порівняння», як для Reflex; `history::compare` з порогом шуму).

## Дизайн

### 1а. Наступний крок у знахідці (бекенд)

- У `optimax_core::Finding` нове поле `next: Option<NextStep>` (`#[serde(default)]`, ts).
- `NextStep` (core):
  - `Compare { variants: [Text; 2] }` — A/B у «Порівнянні»; назви варіантів — ключі i18n
    (напр. «Як зараз» / «Нижча якість тіней і RT»).
  - `Open { tool: Tool }`, `Tool::Upscale` (інших поки немає; enum, щоб не плодити рядки).
- Builder: `FindingBuilder::next(step)`.
- Правило призначення (у `diagnosis`): `Compare` — лише коли порада = налаштування, яке людина
  сама перемикає в грі чи драйвері між прогонами; інакше кроку немає. Попередній розподіл
  (будівельник звіряє з текстами порад і доповнює таблицею в плані):
  - `gpu_bound` → Compare «Як зараз» / «Нижчі налаштування графіки»
  - `vram.near_full`, `vram.stutter` → Compare «Як зараз» / «Нижча якість текстур»
  - `cap.limiter`, `cap.vsync`, `vsync.judder` → Compare за змістом поради (обмеження / V-Sync)
  - `cpu_bound*` → Compare, лише якщо порада про налаштування гри (інакше немає)
  - `upscale.helps` → Open Upscale (замінює наявну кнопку, захардкоджену у `ResultView`)
  - мікрофризи, тротлінг, фонові процеси, Defender, DPC, шейдери → без кроку (не A/B-налаштування)
- Кнопка Reflex у картці затримки лишається як є.

### 1б. Порівняння з попереднім записом (бекенд)

- ~~Поле `vs_previous` у `DiagnosisResult`~~ — змінено під час планування: запис в історію
  зберігається окремим потоком уже після показу результату, тож поле було б ненадійним. Натомість
  потік історії після збереження шле подію `history-saved` з id запису, а команда
  `history_vs_previous(id)` повертає порівняння з **найновішим старішим записом тієї самої гри**
  (`history::compare`, старіший → новіший). Для відкритого з «Історії» запису id відомий одразу.
  Перший запис гри — `None`. Вибір запису — функція `history::previous_of`, покрита тестами.
- Чесність: показуються наявні `threshold_pct` і `trend`; нижче порогу — «у межах шуму»;
  різна сцена/режим монітора — попередження (поля вже є). Підпис картки прямо каже: «один запис
  проти одного; доказ — A/B».

### 1в/2. Результат (фронтенд, `ResultView.svelte`)

```
[смуга показників]
┌ головна картка (8 кол.) ────────────┐ ┌ Проти попереднього запису (4 кол.) ┐
│ вердикт, кільце                      │ │ FPS +8 %  · 1% low +12 %           │
│ ЩО РОБИТИ ДАЛІ                       │ │ поріг шуму 3 % · та сама сцена      │
│ 1 порада …        [Перевірити A/B]   │ │ змінилося: драйвер 566 → 572        │
│ 2 порада …        [Відкрити Апскейл] │ │ один запис проти одного; доказ — A/B│
│ Змінив щось? Запиши ще раз — ми      │ └─────────────────────────────────────┘
│ порівняємо з цим записом.            │
└──────────────────────────────────────┘
ЗНАХІДКИ · N   (пояснення + докази; порада лише якщо її немає вгорі)
▸ Для досвідчених: шкала запису · анатомія кадру · затримка · роздільність
```

- «Що можна перевірити» → «Що робити далі»; до 3 порад, біля кожної кнопка з `next`:
  Compare → перехід у «Порівняння» з пресетом варіантів і грою запису (механізм `expPreset`, як
  Reflex); Open → відповідний розділ.
- Підказка «Змінив щось? Запиши ще раз…» — лише якщо є хоч одна порада.
- Права колонка: картка «Проти попереднього запису», якщо `vs_previous` є; інакше головна картка
  на всю ширину. Бічна плитка другої знахідки й плитка «Розбори» прибираються (дублювали список
  знахідок і згортки).
- Картки знахідок: порада не повторюється, якщо вона вже серед перших трьох угорі.
- Шкала, анатомія кадру, затримка, тест роздільності — всередині однієї згортки «Для
  досвідчених» (закрита за замовчуванням); самі розбори не змінюються.
- Те саме подання — в «Історії» (вона вже використовує `ResultView`).

### 3. Бейджі й кільце «Головної»

- `ui.badge.info`: «Безпечно» → «До відома»; колір бейджа — нейтральний `--text-3` з іконкою
  «i» (зараз зелений). Лічильник на «Головній» — та сама назва. «Безпечно» в очищенні не чіпаємо.
- `AuditReport` нове поле `areas: Vec<AreaResult { check: CheckId, problems: u32 }>` — кожна
  успішна перевірка з кількістю знахідок вище «до відома»; знахідки з `add()` (PawnIO, пам'ять)
  зараховуються до `CheckId::Firmware`. Пропущені перевірки в `areas` не входять.
- Кільце: «без зауважень: X з Y областей» (Y = `areas.len()`, X = з `problems == 0`), замість
  частки «до відома» серед знахідок, яка давала «0 % у нормі».

## Тести

- Rust: `NextStep` для кожного зіставленого id; знахідки без кроку; старий JSON знахідки й
  результату без нових полів читається; вибір попереднього запису (та сама гра, найновіший
  старіший, перший запис → `None`, інша гра ігнорується); `areas` з успіхом/збоєм/`add()`.
- e2e: кнопка «Перевірити A/B» відкриває «Порівняння» з грою й назвами варіантів; кнопка
  апскейлу; картка «Проти попереднього запису» (є / немає / нижче порогу / інша сцена); порада не
  дублюється; згортка «Для досвідчених» закрита й відкривається; бейдж «До відома»; кільце
  «X з Y».

## Залишено будівельнику

- Точні назви варіантів A/B для кожної знахідки й тексти UI (за порадами в `uk.json`).
- Чи зберігати `vs_previous` у файлі запису чи обчислювати при відкритті (рекомендація —
  обчислювати: історія може змінитися після видалення записів).
- Іконки кнопок з наявного набору.

## Рішення, ухвалені мною (не користувачем)

- Порівняння з попереднім — з найновішим старішим записом тієї самої гри, незалежно від сцени
  (різниця сцени — попередження, не фільтр).
- Права колонка «Розбори» й бічна плитка прибираються.
- Інформаційний бейдж — нейтрально-сірий, не зелений.
