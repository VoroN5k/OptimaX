# Служба OptimaX: архітектура й модель загроз (етап 0, на погодження)

Статус: етап 0 погоджено 2026-11-09; **етап 1 зроблено 2026-11-09** (розділ 10). Ідея D15 / E4 з `docs/IDEAS.local.md`.

## 1. Мета

- Інтерфейс працює **без прав адміністратора**: немає запиту UAC при кожному запуску.
- Чорна скринька й постійний журнал продуктивності працюють **без відкритого вікна**.
- Без служби програма працює як зараз (від адміністратора). Служба — необов'язкова.

## 2. Рішення користувача (2026-11-09)

| Питання | Рішення |
|---|---|
| Зміни системи (твіки, очищення, автозавантаження, точка відновлення) | **Через службу**, без UAC на кожну дію. Ризик прийнято свідомо (розділ 6). |
| Де встановлюється служба | Галочка в інсталяторі NSIS + кнопка в портативній версії (exe спершу копіюється в Program Files). |
| Реалізація служби | Крейт `windows-service` (Mullvad, MIT/Apache-2.0). Версію й залежності звірити перед додаванням. |
| Сховище журналу | JSON-файли, як історія записів. SQLite не додаємо. |

## 3. Процеси

```
┌─────────────── сесія користувача ───────────────┐   ┌──────── сесія 0 ────────┐
│ optimax.exe (UI, Tauri, asInvoker)               │   │ optimax.exe --service   │
│  • вікно, оверлей, апскейл, тости, гарячі клавіші│   │ (LocalSystem)           │
│  • активне вікно / процес на передньому плані     │◄─►│  • PresentMon, ETW      │
│  • іконка в треї (агент без вікна, етап 4)        │   │  • метрики, PawnIO      │
│                                                   │   │  • аудит, очищення,     │
│                                                   │   │    твіки, журнал змін   │
└───────────────────────────────────────────────────┘   └─────────────────────────┘
                   іменований канал \\.\pipe\OptimaX
```

**Сесія 0.** Служба не бачить робочого столу користувача: `GetForegroundWindow`, гарячі
клавіші, тости, оверлей, захоплення вікна (апскейл), відкриття Провідника/браузера там не працюють.
Тому:
- усе, що стосується вікон і вводу, лишається в UI-процесі;
- запис гри потребує «процес на передньому плані» — UI надсилає службі PID активного вікна раз на
  тік (звичайне повідомлення каналу); без UI запис іде без перевірки фокуса (чорна скринька в треї
  — UI живий, лише без вікна);
- PresentMon і ETW системні — працюють із сесії 0 (перевірити на етапі 2).

**Той самий exe.** Служба — `optimax.exe --service`, як уже зроблено з `--stability-worker`.
Окремого бінарника немає.

## 4. Код: бекенд без Tauri

Нині команди в `crates/app/src/commands/*` залежать від `tauri::{AppHandle, State, Emitter}`.
Пропозиція:

- новий крейт **`crates/backend`**: `AppState`, логіка команд і `trait EventSink { fn emit(name, json) }`.
  Не залежить від Tauri;
- **режим «у процесі»** (без служби): Tauri-команди викликають бекенд напряму, `EventSink` = Tauri `emit`;
- **режим «служба»**: Tauri-команда пересилає `{cmd, args}` у канал; служба викликає той самий бекенд,
  події йдуть назад каналом і там перетворюються на Tauri-події. UI (Svelte) не змінюється взагалі.

Переносити команди поступово (етап 2 — вимірювання, далі решта), а не все разом.

## 5. Протокол каналу

- Повідомлення: 4 байти довжини (LE) + JSON. Максимум 16 МБ (більші — помилка, з'єднання рветься).
- Запит: `{ "id": u64, "cmd": "...", "args": {...} }`; відповідь: `{ "id", "ok": ... }` або `{ "id", "err": CmdError }`.
- Подія: `{ "event": "...", "payload": ... }` (метрики, прогрес запису, `stab-update`…).
- Рукостискання першим повідомленням: версія протоколу й версія програми. Не збіглися — UI каже
  «оновіть службу» і працює в режимі «у процесі» (якщо має права) або нічого не робить.
- **Закритий перелік команд** (enum на стороні служби). Невідома команда — помилка, не «спробуємо».

## 6. Модель загроз

Служба працює як SYSTEM. Головний ризик — **підвищення прав**: щоб програма без прав
адміністратора через службу зробила те, чого не мала б права.

Захист:
1. **Доступ до каналу (ACL):** SYSTEM, Адміністратори і SID користувача, що встановив службу.
   `PIPE_REJECT_REMOTE_CLIENTS` — з мережі не під'єднатись. Канал створює лише служба
   (`FILE_FLAG_FIRST_PIPE_INSTANCE`), щоб ніхто не підставив свій канал з тим самим іменем.
2. **Перевірка клієнта:** `GetNamedPipeClientProcessId` → шлях образу процесу має збігатися з exe
   самої служби (`%ProgramFiles%\OptimaX\optimax.exe`). Інші програми, навіть від того самого
   користувача, відхиляються.
3. **Ніяких довільних шляхів і ключів від клієнта.** Команди змін приймають лише:
   - id твіка з каталогу (значення, ключ і відкат служба бере з каталогу сама);
   - id об'єкта очищення з її власного скану (служба наново канонізує шлях, перевіряє правило й
     чорний список — як зараз, CLAUDE.md 11.3);
   - id запису автозавантаження з її власного списку.
   Тобто навіть зламаний UI не може попросити «видали C:\Windows» чи «запиши довільний ключ».
4. **Журнал:** кожна зміна — в журнал змін із PID і SID клієнта.
5. **Тека даних:** `%ProgramData%\OptimaX\<SID>` береться з SID **клієнта** (токен з каналу,
   `ImpersonateNamedPipeClient` лише для визначення SID), а не SYSTEM.
6. **Exe служби лише в захищеній теці.** Реєструється тільки `%ProgramFiles%\OptimaX\optimax.exe`
   (пишуть лише адміністратори). Портативна версія при встановленні служби копіює себе туди.
   Інакше будь-яка програма підмінила б exe в «Завантаженнях» і запустилась як SYSTEM.

**Залишковий ризик (прийнято користувачем 2026-11-09):** шкідник, що працює від імені того самого
користувача й **впровадився в процес UI OptimaX** (DLL-ін'єкція), може керувати службою. Межа шкоди
— те, що вміє API служби (п.3): каталог твіків із відкатом, видалення за правилами, автозавантаження.
Довільного коду як SYSTEM API не дає. Без служби такий шкідник того самого не міг би без UAC.

## 7. Встановлення, оновлення, видалення

- `optimax.exe --install-service` / `--uninstall-service` (потрібні права адміністратора).
  Тип запуску — автоматичний (відкладений). **Автозапуск лише за явною згодою** (CLAUDE.md 5.6):
  галочка в інсталяторі за замовчуванням **вимкнена**, у програмі — кнопка з поясненням.
- NSIS: хуки Tauri (`bundle.windows.nsis.installerHooks`, перевірити назву) — перед встановленням
  оновлення зупинити службу, після — запустити; при видаленні програми — видалити службу.
- Оновлення з програми лишається в UI (інсталятор однаково просить UAC).
- Портативна версія: «Встановити службу» → UAC → копія exe в `%ProgramFiles%\OptimaX` →
  реєстрація. «Видалити службу» прибирає і службу, і копію.

## 8. Етапи

0. Цей документ (погодження).
1. **Каркас:** `--service`, встановлення/видалення, канал з ACL і перевіркою клієнта, рукостискання,
   команда `ping`. Кнопка в «Налаштуваннях»: стан служби. Програма поки працює як зараз.
2. **Крейт `backend`** і перші команди через службу: метрики, PawnIO, аудит, запис гри (PresentMon
   з сесії 0, фокус від UI).
3. **Решта команд**, зокрема зміни (п.6.3). Маніфест `asInvoker`; без служби — кнопка
   «Перезапустити з правами адміністратора».
4. **Агент у треї й постійний журнал:** запуск при вході в систему (за згодою), служба сама бачить
   гру зі списку й пише підсумок сесії; чорна скринька без вікна. Заміряти ціну PresentMon у фоні.
5. **Тренди** за тижні й місяці.

## 9. Перевірити до коду (етап 1)

- `windows-service`: версія, ліцензія, залежність (`windows-sys`?), розмір.
- Чи працює PresentMon і наше ETW з сесії 0 (етап 2).
- Хуки NSIS у поточній версії Tauri.
- Чи `PawnIO` дозволяє відкривати пристрій зі служби (SYSTEM — має).

## 10. Етап 1 — що зроблено (2026-11-09)

- Крейт `crates/service`: `protocol` (кадри, `Hello`, закритий `Command` — поки лише `Ping`),
  `pipe` (FFI: `CreateNamedPipeW` з SDDL, `FILE_FLAG_FIRST_PIPE_INSTANCE`,
  `PIPE_REJECT_REMOTE_CLIENTS`, клієнт із `SECURITY_IDENTIFICATION`, PID і шлях процесу на іншому
  кінці), `host` (диспетчер служб, цикл каналу, перевірка клієнта, журнал
  `%ProgramData%\OptimaX\service\service.log`), `install` (стан, встановлення/оновлення, зупинка,
  запуск, видалення), `client` (перевірка, що канал тримає exe з Program Files).
- Дескриптор каналу: SY і BA — повний доступ, користувач — `0x12008B` (`FILE_GENERIC_READ |
  FILE_WRITE_DATA`, без `FILE_CREATE_PIPE_INSTANCE`). Клієнт просить рівно ці права (з
  `GENERIC_WRITE` доступ відхилявся — знайшов інтеграційний тест).
- SID користувача — аргумент служби `--user <SID>` (конфігурацію служби змінюють лише адміністратори).
- `main.rs`: `--service`, `--stop-service`, `--start-service`, `--uninstall-service`.
- Команди `service_status / service_install / service_uninstall`, картка `ServiceCard`.
- NSIS (`crates/app/nsis/hooks.nsh`): перед встановленням — зупинити службу, після — запустити,
  перед видаленням — видалити. **Відхилення від розділу 7:** галочки «встановити службу» в
  інсталяторі немає (потрібен власний шаблон сторінки NSIS) — служба ставиться лише кнопкою в
  програмі, тобто завжди за згодою.
- Тести: протокол (кадри, невідома команда, завеликий кадр), SID у SDDL, справжній канал у
  процесі (привітання, ping, другий «перший екземпляр» не створюється).
- **Не перевірено на реальному Windows:** встановлення служби, запуск як SYSTEM, ping від
  копії з Program Files, відмова копії з іншої теки, хуки NSIS під час оновлення.
