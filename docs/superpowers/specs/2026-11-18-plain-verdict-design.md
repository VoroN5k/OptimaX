# Вердикт простими словами — дизайн

Дата: 2026-11-18. Етап 2 «простого шляху для звичайного гравця» (етап 1 — бібліотека ігор — готовий).

## Навіщо

Зараз результат запису відповідає на питання інженера: «що обмежує FPS — ядро в стелі 63 %, GPU 54 %»,
кільце, докази, графіки, анатомія кадру. Звичайний гравець із цього не зрозуміє, **чи все в нього
нормально, чому були ривки і що зробити**. Користувач: «є купа графіків, але що людина з цього
зрозуміє і зробить?»

Програма сама складає з усіх наявних метрик коротку розповідь людською мовою. Графіки й поточний
інженерний вердикт лишаються для тих, хто хоче копнути, — у згортках.

## Цілі

- Зверху результату — розповідь із трьох частин: **«Як іде гра»**, **«Чому були ривки»**, **«Що
  зробити»** (одна головна дія + «Інші варіанти»).
- Розповідь складає бекенд (`diagnosis`, чиста функція); інтерфейс лише показує тексти.
- Чесно: причина ривка — збіг у часі («найімовірніше», «збіглося з», «у 7 з 10 ривків»), а не
  доведений факт. Немає причини — так і кажемо.
- Працює однаково в «Чому лагає?» і в «Історії» (спільний `ResultView`).

## Не цілі

- Перемикач «Простий / Експертний» для всієї програми — етап 4. Тут лише згортки.
- Сценарій «Перевірити мою гру» на «Огляді» і «було / стало» — етап 3.
- Нові вимірювання, нові правила діагностики, зміна наявних вердиктів і їхніх порогів.

## Антицілі (провал, навіть якщо «працює»)

- Розповідь стверджує причину як доведену («ривки через диск») або обіцяє приріст FPS.
- Розповідь суперечить знахідкам нижче (інша причина, інша порада, інша оцінка ривків).
- Нові «на око» пороги («60 FPS — добре»): оцінки беруться лише з наявних правил.
- Логіка складання розповіді у фронтенді (CLAUDE.md 10.8).

## Підходи (обрано користувачем: 1)

1. **Окрема чиста функція в `diagnosis` → нове поле `Diagnosis.story`** (обрано). Складається під
   час діагностики, коли ще є структуровані причини ривків (тип, частка збігів), тож тексти точні й
   тестуються на штучних даних і записах RE9.
2. Розповідь як ще одна «знахідка» в списку — без нової розмітки, але три частини втискаються в
   «заголовок / опис / докази»; криво й важко розвивати.
3. Складання в інтерфейсі зі знахідок — заборонено правилами проєкту (логіка вердиктів лише в
   бекенді); до того ж у готовому результаті причини вже лише текстом.

Розміщення (обрано користувачем: А): розповідь **замість** головної картки; нинішні смуга
показників, вердикт із кільцем, докази й знахідки — у згортці «Детальніше».

## Як це працює

### Дані (бекенд, `crates/diagnosis`)

Новий модуль `story.rs`, тип із `ts`-derive, поле `Diagnosis.story: Option<Story>`
(`#[serde(default)]`, щоб старі JSON-и читались). Записи «Історії» перераховуються з сирого запису
(`history.rs` викликає `diagnose`), тож розповідь з'явиться і для старих записів.

```rust
pub struct Story {
    pub smoothness: Smoothness,   // оцінка плавності
    pub outcome: StoryOutcome,    // чи це проблема
    pub how: Vec<Text>,           // «Як іде гра»: 1–3 речення з цифрами
    pub why: Vec<StoryCause>,     // «Чому були ривки»: до 3 причин, порожньо — ривків немає
    pub why_unknown: bool,        // ривки є, а причину не знайдено
    pub action: Option<u32>,      // індекс у `Diagnosis.verdicts` — головна дія
    pub others: Vec<u32>,         // індекси «Інших варіантів»
}
pub enum Smoothness { Smooth, Isolated, Noticeable, Severe }
pub enum StoryOutcome { Fine, Fixable, Unexplained, Insufficient }
pub struct StoryCause {
    pub code: String,     // CauseKind::code(): зв'язок із радаром/шкалою
    pub text: Text,       // готове речення з аргументами
    pub likely: bool,     // головна (≥ 50 % ривків) чи часткова
    pub hits: u32,        // у скількох ривках
    pub of: u32,          // з-поміж скількох
}
```

Дія посилається на знахідку **індексом**, а не id: id повторюються (кілька `background`).
Інтерфейс бере з цієї знахідки пораду (`advice`) і кнопку наступного кроку (`next`) так само, як
зараз у «Що робити далі».

### Оцінка плавності — лише наявні правила

| `Smoothness` | Коли (наявне правило) |
|---|---|
| `Smooth` | `rules::stutter` нічого не дав (ні мікрофризів, ні поодиноких ривків) |
| `Isolated` | лише `stutter.isolated` (Info): кілька окремих ривків, часто завантаження |
| `Noticeable` | `stutter.*` з впливом `Moderate` (1 % low < 50 % середнього і ≥ 3 ривки, або ривки ≥ 1 % кадрів і ≥ 5) |
| `Severe` | `stutter.*` з впливом `High` (1 % low < 35 % середнього) |

Оцінка виводиться з результату `rules::stutter` (його id і впливу), а не обчислюється заново, —
так розповідь не може розійтися зі знахідкою.

### «Як іде гра» (`how`)

Лише факти з цифрами, без оцінок «добре / погано» для FPS (порогу «достатньо FPS» немає й не
вигадуємо):

1. Середній FPS і частота монітора, якщо відома: «В середньому 87 кадрів/с, монітор — 144 Гц».
   При `Bottleneck::FrameCap` — «FPS тримається на ліміті ≈60». Без частоти — без її згадки.
2. Речення плавності за `Smoothness`: «Ривків не було» / «Було 2 окремі ривки, перший на 3,1 с —
   часто це підвантаження» / «Помітні мікрофризи: у найгірші моменти 31 кадр/с замість 87» /
   «Сильні мікрофризи: …». Цифри — 1 % low, середнє, кількість ривків, найдовший кадр.
3. Що обмежує, простими словами, за `bottleneck`: «Відеокарта працює на межі — це її стеля, а не
   несправність» / «Гра впирається в процесор» / «FPS обмежує ліміт у грі чи V-Sync» / «Нічого
   явно не обмежує». Нового порогу впевненості немає: речення є для будь-якого вердикту, крім
   `InsufficientData`; межовий випадок (впевненість 60 %) — «схоже, відеокарта…». Число
   впевненості — у «Детальніше».

Для поодиноких ривків — та сама думка, що в наявному `stutter.isolated` («ривки на старті часто
дає завантаження рівня або компіляція шейдерів»), без сильнішого твердження.

Генерація кадрів: цифри вже за шкалою, яку бачить око (`frame_gen`), — розповідь бере ті самі
`stats`.

### «Чому були ривки» (`why`)

Береться та сама класифікація причин, що й у `rules::stutter` (`correlated_causes`: головні ≥ 50 %
ривків і вдвічі частіше за звичайне, часткові, «як завжди»). Потрібно винести її в спільну функцію,
яку викликають і `stutter`, і `story`, — **одне обчислення, одні межі**.

- Головні → `likely = true`, речення «Найімовірніше — компіляція шейдерів: збіглося з 7 з 10
  ривків». Часткові → `likely = false`, «Частина ривків (3 з 10) збіглася з активністю диска».
  «Як завжди» — у розповідь не йдуть (вони ривків не пояснюють).
- До 3 причин: головні, потім часткові, за часткою збігів.
- `hits = round(at_spikes × кількість ривків)`, `of` = кількість ривків, за якими рахувався збіг.
- DPC із відомим драйвером — назва в реченні (як у наявній пораді `driver_kind`).
- Ривки є (`Noticeable`/`Severe`), причин немає → `why_unknown = true`, текст «Причину не знайдено:
  ривки ні з чим виміряним не збіглися».
- `Smooth`/`Isolated` → `why` порожній, блок не показується.

### «Чи це проблема» (`outcome`) і «Що зробити»

Кандидати — знахідки з `verdicts` (крім підсумку `[0]`), що мають пораду (`advice`), у наявному
порядку (вплив, далі впевненість). `stutter.unknown` — особливий: його порада не виправлення, а
«що ще може бути + запишіть ще раз», тож до `Fixable` він не зараховується.

- `Fixable` — є кандидат (не `stutter.unknown`) із впливом ≥ `Moderate`. `action` = перший такий;
  `others` = решта кандидатів (будь-якого впливу).
- `Unexplained` — таких немає, але `why_unknown`. `action` = знахідка `stutter.unknown` (її порада:
  оверлеї, підвантаження світу, повторний запис); `others` = решта кандидатів.
- `Fine` — ні того, ні іншого: «Усе гаразд: це межа вашого заліза, налаштування Windows тут не
  допоможуть». `action` = `None`, `others` = кандидати з `Info` (напр. апскейл для відеокарти —
  «якщо хочете більше FPS»).
- `Insufficient` — `Bottleneck::InsufficientData`: розповідь лише з поясненням «запис закороткий /
  гру не знайдено», без `why` і дій.

Порада й кнопка беруться з самої знахідки — тексти порад не дублюються в розповіді.

### Інтерфейс (`ui/src/components/ResultView.svelte`)

```
┌ Розповідь ─────────────────────────────────────────┐
│ [бейдж: Плавно / Поодинокі / Помітні / Сильні ривки]│
│ Як іде гра                                          │
│   В середньому 87 кадрів/с, монітор — 144 Гц.       │
│   Помітні мікрофризи: у найгірші моменти 31 …       │
│ Чому були ривки                                     │
│   Найімовірніше — компіляція шейдерів (7 з 10)      │
│ Що зробити                                          │
│   ① <порада знахідки>            [кнопка next]      │
│   Інші варіанти ▸                                   │
│ 60 с записано · гра закрилась посеред запису        │
└─────────────────────────────────────────────────────┘
[Порівняння з попереднім записом — як зараз]
▸ Детальніше      — смуга показників, вердикт із кільцем і доказами, усі знахідки
▸ Для досвідчених — шкала, графік, анатомія, затримка (як зараз)
```

- Нова картка `StoryCard.svelte` на базі `HeroCard` / наявних токенів. Бейдж плавності — текст +
  іконка, не лише колір (`--ok` плавно, `--warn` ривки).
- «Інші варіанти» — `Disclosure`, згорнуто.
- Рядок під карткою — те, що зараз у підвалі смуги показників (зарахований час, причина завершення).
- «Детальніше» — нова згортка (`Fold`) з тим, що зараз угорі: `KpiStrip`, `HeroCard` з кільцем і
  доказами, список знахідок. За замовчуванням згорнута; етап 4 вирішуватиме це глобально.
- «Для досвідчених» — без змін, окремою згорткою нижче.
- Якщо `story` немає (`null`) — показати як зараз (запасний шлях, без помилки).
- Позначки знайомства (`data-tour="diag-stats"`, `diag-summary`) — перенести на розповідь так, щоб
  тур не вказував у згорнутий блок.

Ключі `diag.story.*` у `crates/core/locales/uk.json`; `npm run check:i18n` має проходити. Без

## Обмеження

- CLAUDE.md: без `unwrap`/`panic` у продакшн-коді, `forbid(unsafe_code)`, doc-коментарі публічних
  типів, `fmt` / `clippy -D warnings`, лише токени в UI, українська.
- `diagnosis` — чисті функції без системних викликів.
- Нових залежностей немає.
- Чесність (CLAUDE.md 6): впевненість і докази лишаються в «Детальніше»; розповідь не прибирає
  «збіг у часі» з формулювань.

## Перевірка

- Модульні тести `story.rs`: кожна `Smoothness`, кожен `StoryOutcome`, причини головні / часткові /
  «як завжди» (остання не потрапляє), DPC із драйвером, `FrameCap`, без частоти монітора,
  недостатньо даних, індекси дій вказують на знахідки з порадою.
- Тест узгодженості: на тих самих даних причини в `story.why` і в доказах `stutter.*` збігаються.
- Записи RE9 (`tests/recordings/*.toml`): додати очікування `smoothness` / `outcome` (значення —
  після першого прогону, звірені з графіком; не підганяти під код без перегляду).
- e2e (Playwright): розповідь видно одразу; «Детальніше» розгортає кільце й знахідки; кнопка
  головної дії працює (`compare` / `open upscale`); запасний шлях без `story`. Наявні тести, що
  шукають вміст головної картки, — спершу розгортати «Детальніше».
- Ручна перевірка користувачем на реальній грі: чи зрозуміла розповідь, чи збігається з графіком.
